## Rules (as implemented and tested)

- Key: exactly `(camera_id, track_id)` per AI_SPEC §5.
- `None` policy: `track_id=None` observations are IGNORED — no key created,
  other keys untouched. Rationale (in the module docstring): history must be
  keyed by track identity, and unassigned detections are routine (occlusion,
  track birth/death), so raising would be hostile to the live loop. Explicit
  and tested, never silent.
- Append/ordering: first observation per key always accepted;
  `timestamp >= last` appended (duplicates accepted in arrival order);
  `timestamp < last` → fail-closed `ValueError` naming the key and both
  stamps, store unchanged. Compared per-key only (cross-key independence).
- Eviction: per-key `deque(maxlen=...)` — full buffer drops OLDEST
  automatically, newest always retained. Count-based only; time-based expiry
  is P3-004 (documented).
- Boundedness: storage is exactly one dict of `maxlen` deques — memory is
  bounded by `(#keys) x max_observations`, no unbounded structure anywhere
  (key material lives only in the dict; reads build transient tuples).
- Reads: `snapshot` returns a fresh oldest→newest tuple (`()` for unknown
  keys); `keys()` first-seen order; `__len__` = number of tracked keys;
  `remove` bool + `clear` deterministic; `__repr__` scalar-only (counts/keys,
  no confidences dump); single-owner, no locks (the bounded frame queue
  remains the thread-safe handoff).

## Default rationale

`max_observations=60` is an ENGINEERING default, not a calibrated fall
threshold (recorded in the `TrackHistoryConfig` docstring): AI_SPEC §9
bootstraps `tracking.history_seconds: 2.0`, and at typical fixed-camera
rates of 15–30 fps a 2 s window holds ~30–60 observations — so 60 covers
the full 2 s window at 30 fps (about 4 s at 15 fps) while staying a small
constant per track. Configurable per store; eviction stays count-based.

## Assumptions

- Default 60 covers the AI_SPEC §9 `history_seconds: 2.0` example at
  15–30 fps; if the pipeline's real frame rate differs, the capacity (not
  the semantics) is re-tuned with measured evidence.
- `snapshot`/`remove` reject `track_id=None` with `TypeError` (fail-closed):
  `None` is an append-time condition, never a valid stored key, so lookup
  APIs treat it as a caller bug rather than an empty result.
- `keys()` first-seen (insertion) order is relied on only for determinism
  assertions, not for semantics; `remove` does not reorder survivors.
