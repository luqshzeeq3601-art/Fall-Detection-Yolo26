## 2. Timing table (fields / units / boundaries)

All values MILLISECONDS (never seconds).

| Field | Unit | Boundary (stamps) | Notes |
| --- | --- | --- | --- |
| `predict_ms` | ms | `t0` = pre-predict → `t1` = post-predict | `(t1 - t0) * 1000.0`; model prediction only |
| `adapt_ms` | ms | `t1` = pre-adapt → `t2` = post-adapt | `(t2 - t1) * 1000.0`; `adapt_pose_results` only |
| `total_ms` | ms | `t0` → `t2` | `(t2 - t0) * 1000.0`; predict + adapt only |

Explicitly NOT measured (never stamped, never included): frame acquisition
latency, queue waiting time. `timing=None` means unmeasured and occurs only on
hand-constructed results; every pipeline-produced success result carries a real
`PoseTiming`. Read-failure / empty-queue paths return `None` with zero timer
calls; predictor / adapter failures raise with no result and no timing object.
Backwards (`t1 < t0`, `t2 < t1`) or non-finite stamps fail closed with a naming
`ValueError` — never a negative or clamped duration.

## 7. Assumptions

- A1 (disclosed reconciliation): the brief prescribes `t = [100.0, 100.010,
  100.025]` → exactly `10.0 / 15.0 / 25.0` ms. In binary floating point the raw
  scale-up yields `10.000000000005116`, so a pure `(t1 - t0) * 1000.0` formula
  cannot satisfy exact equality. `timings_from_stamps` therefore normalizes each
  duration with `round(..., 9)`, which discards only sub-picosecond dust far
  below any clock resolution while making controlled-stamp math exact. Ordering
  is validated on the RAW stamps before rounding, so the fail-closed anomaly
  policy is unaffected. Zero-duration stamps still yield true `0.0`.
- A2: `t2` is taken immediately after `adapt_pose_results` (before the
  `orig_shape`/image cross-check), so `total_ms` covers exactly predict + adapt
  and `total == predict + adapt` holds on controlled stamps.
- A3: Timer-call consumption contract — success: 3 calls; predictor failure:
  1 call (`t0` only); adapter failure: 2 calls (`t0`, `t1`); read-failure /
  empty-queue `None` paths: 0 calls. All asserted in tests.
- A4: Stamps require finiteness + ordering only (no `>= 0` policy — stamps are
  opaque clock readings); `PoseTiming` fields additionally require `>= 0`.

## 8. Limitations

- Timings measure in-process predict + adapt durations only; they exclude frame
  acquisition, queue waiting, the pipeline cross-check/log overhead, and any
  downstream consumer. They must not be read as end-to-end or hardware
  performance figures (none are recorded anywhere in code, tests, or this report).
- With the real default timer, consecutive identical-stamp collisions are
  possible at clock granularity; determinism in tests comes solely from the
  injected `FakeTimer`, never from the wall clock.
- `round(..., 9)` quantizes durations below one picosecond of a millisecond
  (10⁻¹⁵ s order); this is orders of magnitude beneath real clock resolution
  and loses no measurable information.
