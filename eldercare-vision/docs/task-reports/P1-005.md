## 1. Delay formula + worked example

Deterministic, NO jitter:

```text
delay_for(attempt) = min(base_delay * multiplier ** (attempt - 1), max_delay)
```

Defaults (`base_delay=1.0`, `multiplier=2.0`, `max_delay=30.0`):

| attempt | raw exponential | returned |
|---|---|---|
| 1 | 1.0 | 1.0 |
| 2 | 2.0 | 2.0 |
| 3 | 4.0 | 4.0 |
| 4 | 8.0 | 8.0 |
| 5 | 16.0 | 16.0 |
| 6 | 32.0 | **30.0** (cap flattens) |
| 7+ | 64.0+ | **30.0** (cap flattens) |

Why no jitter: single-camera local POC — reproducible timing beats
thundering-herd avoidance here. Jitter is a documented later option,
not implemented (backoff tuning is benchmark-driven work for a later task).
`OverflowError` on astronomically large attempts (float `**` overflow)
returns `max_delay` directly (pinned by `test_2e`).

## 2. Honesty rule

A successful `capture.open()` resets `attempts`/`consecutive_failures`
to 0 and `last_delay` to `None` (logs `stream.reconnect.recovered`) but
**never writes the `StreamHealthMonitor`**: open-success ≠ health-ONLINE.
The monitor recovers only on real frames via `notify_frame`. Pinned by
`test_8`: health driven `UNKNOWN → DEGRADED → OFFLINE` by polls stays
`OFFLINE` (with `last_frame_at is None`, `poll()` → `None`) across a
successful `attempt()`; the next `notify_frame` yields exactly one
`OFFLINE → ONLINE`, with full transition-list equality asserted.

## 6. Design decisions

- **Both override spellings accepted**: brief body specifies
  `connect_with_retry(max_attempts_override=…)` while test area 4 calls
  `connect_with_retry(max_attempts=3)`; the implementation accepts both
  keywords (must agree when both given, else `ValueError`) with
  precedence override → alias → `policy.max_attempts`. Both spellings
  are pinned by tests.
- **`stop()` logs once**: the first `stop()` transition logs
  `stream.reconnect.stopped` (INFO); repeats are silent, and
  `connect_with_retry` does not re-log on stopped exit (no dup noise).
- **No I/O under the lock** (same convention as `queue.py`/`health.py`):
  stopped checks and counter updates are locked; `capture.open()`,
  logging, and `sleep()` happen outside it.
- **Logs carry numeric/id fields only** (`attempt`, `max_attempts`,
  `delay`); `__repr__` renders `camera_id/attempts/consecutive_failures/
  stopped` — the held `CameraConfig` URL is never formatted
  (plus sanitizer defense-in-depth on the rendered `camera_id`).
- **No `try/except` around `capture.open()`**: `RtspCapture` already
  contains `Exception` failures (returns `False` + sanitized
  `last_error`); `BaseException` propagates by design, matching
  `capture.py`'s cancellation philosophy.

## 7. Assumptions

- `RtspCapture.open()` never raises `Exception` (its documented
  contract); the controller relies on it and adds no second containment
  layer.
- `clock` is stored for DI/signature stability and future manager
  integration; current timing needs no wall-clock reads (delays come
  from the policy), so the fake clock is wired but unticked by the
  controller itself.
- `max_attempts=True` (bool) is rejected as a non-int cap — a bool cap
  is treated as a caller bug.

## 8. Limitations

- Single-driver model: like `RtspCapture`, the controller assumes one
  loop thread drives `attempt()`/`connect_with_retry`; the lock only
  protects flag/counter races (e.g. `stop()` from another thread).
- `policy.max_attempts=None` retries forever until success or `stop()`
  — callers must guarantee a stop path.
- No jitter, no attempt timestamps/durations, no events/persistence/
  telemetry (explicitly out of scope: Phase 7 / Phase 5 / P1-006).
