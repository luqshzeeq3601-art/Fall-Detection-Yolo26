## Findings

### Minor

- **[Minor] M1 — Non-numeric thresholds raise `TypeError`, not the brief's `ValueError`.**
  `src/eldercare/vision/stream/health.py:122` — `if not 0 < degraded_after < offline_after:` performs chained comparison directly, so `degraded_after="x"` raises `TypeError: '<' not supported between instances of 'int' and 'str'` (confirmed live) instead of `ValueError` naming the relation. The brief (§`__init__`) says "validate `0 < degraded_after < offline_after` else `ValueError` naming the violated relation". The brief's test area 9 only pins numeric bad values (equal/zero/negative — all correctly `ValueError`), so this is out of the tested contract, but a strict reading covers "any violation". Suggested (not required): coerce/guard with `isinstance((int, float))` + `math.isfinite`-style check first and raise the same `ValueError`. Related: `degraded_after=True` is accepted (bool is int, `True == 1`) — same root, negligible in practice since thresholds come from config defaults. Not a blocker.
